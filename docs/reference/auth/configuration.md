# Auth Control Plane configuration and secret-file reference

`auth-service --help` prints the same registry. A **flag overrides the
environment variable** for the same setting. Secrets have no flag, because
process arguments are readable by anyone who can run `ps` or `docker top`.
**The environment is readable too** (`docker inspect`, `/proc/<pid>/environ` for the same
user), so a DSN given as an environment variable is exposed to anyone with that
access; the local Compose profile does this for its development defaults. For
anything else use the `_FILE` form with a mounted secret.
Non-secret settings supplied only through the environment make the service log
one startup warning listing their names, so a deployment configured that way is
not invisible.
{: .fc-page-lede }

## auth-service

A **syntactic** fault (both a secret and its `_FILE`, an unparseable duration, a
malformed address, a missing required setting, a value out of bounds) stops the
process before it starts, with exit code 1. A **dependency** fault (an
unreachable database, a missing or unsafe key file) does not: the process starts
and `/readyz` fails closed, naming the check. See the
[readiness reference](readiness-and-slo.md).

### Session route bearer

The session, social link and change-password routes read their bearer through the route's endpoint-profile row. With `AUTH_TOKEN_ISSUER_URL` set, they accept the EdDSA user access token of audience `auth-service` (access-token.v1), checked against the keys the JWKS publishes: it needs a valid `sid`, its session must be live, and the session's `token_version` pin must equal the user's current `token_version`. The HS256 compatibility access token stays accepted on the same rows. Without `AUTH_TOKEN_ISSUER_URL` the routes verify the HS256 compatibility access token only.

A password change issues the caller's new session in the organization of the session it replaces only while the caller is still a member of that organization; if the membership is gone, the new session has no organization, as in go-api.

The session routes accept the EdDSA token with audience `auth-service` only, and go-api and query-api one with audience `dev-health-api` only. Under the eddsa class the service therefore mints both for one session: `access_token` (audience `AUTH_JWT_AUDIENCE`, `dev-health-api`) and `session_access_token` (audience `auth-service`), same sid and lifetime; each token's signing kid is recorded on the session (a key rotation between the two signs can give them different kids, both published). `/v1/token/refresh` answers `refresh-response.v2`; go-api's wire answers (login, refresh, social, SSO, change-password, and go-api's own sign-ins through the issue route) add `session_access_token` as their last member. With the session routes mounted the service refuses to start with the eddsa class and `AUTH_JWT_AUDIENCE=auth-service`, which every go-api and query-api row would refuse. A client sends `session_access_token` as the bearer of the session routes, `/api/v1/auth/change-password` and the social link routes.

### Rate limits

The login, credential and social link routes count in a shared fixed-window store, so a limit holds across replicas. Every counter id starts with `auth_svc_`; go-api's counters are never read or written.

- **Store login.** Give auth-service its own Valkey ACL login, limited to its prefix, and put its URI in the `AUTH_VALKEY_URI` Secret (the chart takes it by `secretKeyRef`, `authService.valkey`): `ACL SETUSER auth-service-ratelimit on >PASSWORD resetkeys ~dho:rl:auth_svc_* resetchannels &auth_svc_* -@all +hello +select +ping +get +eval +incr +decr +pexpire +hget +hset +publish +subscribe +client|tracking (~dho:rl:auth_svc_rev_hwm +hgetall)`.
- **In-chart Valkey.** `ACL SETUSER` on a running Valkey is lost at the next restart. With the chart's own Valkey, set `valkey.acl.enabled=true` with `valkey.acl.secretName` (and `valkey.acl.secretKey`, default `users.acl`): the chart then starts Valkey with `--aclfile` on that Secret key, so the users survive a restart. The render refuses `enabled` with an empty name or key, and nothing refers to the Secret while `enabled` is false. The file defines every user: the `default` user line (`user default on nopass ~* &* +@all`, unchanged from today, which the probes and the other planes use) and `user auth-service-ratelimit on #<sha256 hex of the password> <the rule above>`, with a hashed password, never the plain one. The Secret is created outside the chart first, holds the service's `AUTH_VALKEY_URI` under its own key, and each pod reads only its own key. Limit: the default user keeps every key, so it can still read and write the `auth_svc_` counters; what bounds who can do that is the network policy, not the ACL, so the render refuses `valkey.acl.enabled` unless `networkPolicy.enabled` is true. That policy admits every pod of the release namespace, so it does not isolate other clients in the same namespace. The Secret file is mounted with mode 0444 (it holds hashes only). Enabling restarts the Valkey Deployment once. Rotation: a changed Secret does not roll any Deployment and Valkey keeps its loaded users; after you change the Secret, either restart the Valkey Deployment or run `ACL LOAD` on it once the mounted file shows the new content (the kubelet refreshes it within about a minute). A changed `AUTH_VALKEY_URI` needs a new auth-service pod, because it is an environment variable.
- **Limits.** Login: 20 per 15 minutes per client address, 10 per 15 minutes per client address and account. Compatibility refresh: 10 per 15 minutes per client address (go-api's `auth_refresh` budget; counted after the body is validated, so a refused body costs nothing). Reset password: 20 per hour per client address, 5 per hour per client address and link secret. Verify 10, resend 3, forgot 3, change password 5 per hour (as go-api); resend and forgot also 20 per hour per client address across all e-mails (go-api has none). Social link and unlink: 10 per hour per client address and signed-in principal. A body that fails validation (or an unlink id that does not parse) costs nothing; verify counts per client address only, never by a value in its query.
- **Keys.** The client address is the socket peer, or, when the peer is in `AUTH_SERVICE_TRUSTED_PROXIES`, the right-most `X-Forwarded-For` hop that is not itself listed (go-api resolves its own client address with the same rule). A hop that is not an address ends the walk and the peer is the client. A list entry is `/28` or longer (IPv6 `/124`) freely; an IPv4 `/24`..`/27`, such as the node pod range, needs `authService.trustedProxiesWideAccepted: true` and its node exclusions; anything wider, and any IPv6 network wider than `/124`, is refused at render. An entry `!<address>` excludes one address inside a listed network: it is never trusted. The node pod range holds the node's own addresses (the network address and the bridge at the next one), from which a host process or a hostNetwork pod reaches the API port past the go-api pod selector, so a wide entry renders only with both: `["10.42.0.0/24", "!10.42.0.0", "!10.42.0.1"]`. The service refuses to start on a `/0` network or any IPv4-mapped entry. go-api reads its own `TRUSTED_PROXIES` with the same parser and refuses to start on a list it cannot read (no entry is dropped); its start line logs `api: trusted proxies entries=N exclusions=M`. A literal `goApi.extraEnv` `TRUSTED_PROXIES` value is checked at render with the same rules, the ack band aside. The rule holds at every `authService.phase`, the proxy off included; the ack changes nothing for a list of narrow entries. The address list trusts every pod in a range as a proxy, so the auth-service NetworkPolicy (go-api pods alone on the API port) is the boundary. An IPv6 client is keyed by its /64. Accounts, link secrets and principals enter a key as an HMAC-SHA256 digest (128 bits), never as written. The HMAC key is derived by HKDF-SHA256 from `AUTH_JWT_SECRET_KEY` (info `dev-health/auth-service/ratelimit-key/v1`), so there is no Secret of its own; it is used for nothing else and is never logged or exported. **Rotating `AUTH_JWT_SECRET_KEY` changes every digest and so resets every bucket** (a rotation window grants each caller a fresh budget).
- **Client-address proof.** `AUTH_CLIENT_ADDR_MODE` (`cidr` default, `both`, `signed`) and `AUTH_CLIENT_ADDR_VERIFY_KEY` (one or two `<kid>:<key>` entries; `_FILE` reads a mounted file) let auth-service name the client from the `X-Forwarded-Client-Proof` that go-api sends with `AUTH_CLIENT_ADDR_SIGNING_KEY`, instead of from the trusted-proxy list. Mode `cidr` is the rule above (a proof is counted only); `both` takes a valid proof, else the rule above; `signed` takes a valid proof, else the socket peer, and reads the trusted-proxy list only for `GET` and `HEAD` of the two well-known documents. See the [client-address proof runbook](../../operate/runbooks/auth-client-address-proof.md).
- **Refusal.** Past a limit the route answers `429` with the `rate_limited` envelope, which names no limit and no key. A store error answers `500` (closed) and counts in `dev_health_api_rate_limit_store_errors_total{limit}`; the series carries the limit id only.

### Session issue route

With the compatibility routes mounted, auth-service also serves `POST /internal/v1/sessions`. go-api calls it, while auth-service owns sessions (`AUTH_PROXY_SESSIONS`), for the sign-in flows go-api still serves (login, switch-org, accept-invite, change-password, social and SSO login).

- The route, the session state route and the two delegated routes are mounted only with `AUTH_SESSION_ISSUE_WORKLOAD_SUBJECT` set (a workload principal id, `prn_` and 22 base64url characters; it needs `AUTH_TOKEN_ISSUER_URL`; `AUTH_SESSION_ISSUE_WORKLOAD_SUBJECT_FILE` reads it from a mounted file instead, and setting both is refused). The caller presents the go-api workload token: header `typ` `workload+jwt`, audience `auth-service`, `sub` equal to that value, signed by the auth-service key set. No table is read to decide it. Every other credential (a user or edge access token, `fcacr_`, `fcpush_`, `fcwlb_`, `whsec_`, `dhr1_`, any `svc_`) and every wrong audience, subject, signature or time is the same `401` envelope; a key set that cannot be read is `503`. The audit row names the workload principal as actor and `workload_jti`.
- The read listing route `POST /internal/v1/principals/readable-repositories` takes the same go-api workload token and nothing else. Its body is `{"principal_id", "organization_id"}` (two canonical UUIDs); its answer, `readable_repositories.v1`, is the repositories that principal may read in that organization through `acr.context.read`, by the rule of `POST /v1/authorize:repositories`: `scope` `organization`, `repositories` with the principal's own canonical keys (at most 256), or `denied` with the read decision's `reason_code` (`repository_allowlist_too_large` above 256 keys, never a truncated list). Every call reads the state again in one read-only transaction; there is no decision cache and no catalog read. A state failure is `503 store_unavailable`. It mounts only when its endpoint-profile row lists exactly `workload_token`; without the row it answers 404 and the startup log has an Info line `auth readable repositories route not mounted`. go-api's principal access read calls it on every user-class read (roll order: auth-service first, then go-api).
- The session issuer credential (`svc_authsess_`) is retired on these four routes: it is refused from the bearer text alone, before any store or key-set read, with the same `401`, and `auth.session.retired_credential_refusals{operation}` counts each refusal (declared at 0 for `session_issue`, `session_state`, `delegated_session_start` and `delegated_session_end`). A non-zero count names a caller that still presents it.
- Session issue credential (go-api): with `AUTH_PROXY_SESSIONS=true`, go-api's session issue call presents go-api's workload token (audience `auth-service`), asked of the workload client on every call; it reads no `AUTH_SESSION_ISSUE_TOKEN`, and every other header of the issue call, the end user's client address included, is the same as before. `AUTH_SESSION_ISSUE_CREDENTIAL` may be unset, empty or `workload`; `session_compat` (the retired credential) and any other value are a start-up error naming the variable, a padded or whitespace-only value included (the value is compared as it is). The workload inputs are the ones of the provisioning credential below (`AUTH_WORKLOAD_SUBJECT_FILE` or `AUTH_WORKLOAD_BOOTSTRAP_FILE`, `AUTH_WORKLOAD_ISSUER`), and when both selectors choose `workload` one workload client and one exchange serve both. A missing or invalid input is a start-up error naming the variable; a failed exchange fails the sign-in as 503 with no request to the route and no fallback to `svc_authsess_`.
- The body is `principal_id`, `organization_id` (a UUID or `null`) and `amr`, and optionally `predecessor_session_id` (a lowercase UUID, the caller's own session); any other member, a missing one or a duplicate is `401 malformed`. The user must exist and be active, and, with an organization, be a member of it (403 otherwise). An organization whose slug another auth organization holds is `409 organization_conflict` (an ERROR line; it needs an operator), on this route, the delegated route and the compatibility sign-ins (`POST /api/v1/auth/login`, switch-org, social and SSO sign-in: go-api's `{"detail": ...}` 409); go-api's own sign-in answers its 503 for that refusal. With `predecessor_session_id`, the issue supersedes that session (an organization switch): under the predecessor's row lock auth-service revokes it and every refresh credential of it, creates the new session, and writes the `auth.session.issued` row and one `auth.session.revoked` row (`target_id` = the predecessor) in **one** transaction. A predecessor that is unknown, revoked or expired is `401 session_revoked` and nothing is written, so two concurrent switches from one session leave at most one live successor; a predecessor of another principal is `403 not_entitled`. No other session of the user is touched. go-api's switch-org sends the caller's own session (the `sid` its access token names, checked live) and answers `401` when the predecessor ended first; a token without `sid` sends no predecessor. The other sign-in flows never send one.
- The session is pinned to the user's `token_version` and created with one `auth.session.issued` audit row (`source` `go-api-delegated`, the `amr`, the workload principal as actor and the token's `workload_jti`, the end user's client address and user agent) in one transaction. The answer is `{"access_token", "refresh_token", "token_type": "bearer", "expires_in"}`.
- Chart: with sessions on, the chart always renders `AUTH_SESSION_ISSUE_CREDENTIAL=workload` and no other session issue credential: the workload token is the only mode. `goApi.sessionIssue.credential` (`workload` or `""`) and the retired `secretName` and `secretKey` keys are accepted and change nothing, so a values file that sets them renders unchanged. `goApi.extraEnv` cannot set the name, in any spelling.
- Credential steps: set `AUTH_SESSION_ISSUE_WORKLOAD_SUBJECT` on auth-service to go-api's workload principal, and give go-api its workload inputs (`AUTH_WORKLOAD_SUBJECT_FILE` or `AUTH_WORKLOAD_BOOTSTRAP_FILE`, `AUTH_WORKLOAD_ISSUER`). A `sessions:issue` row of `internal_service_credentials` is no longer used by any route; it stays until a later migration drops the table.

### Provisioning routes

With `AUTH_MEMBERSHIP_ROUTES=true`, auth-service serves the membership, invite and organization writes go-api makes while auth-service owns users: `POST /internal/v1/memberships/{add,role,remove,transfer}`, `POST /internal/v1/invites/{create,accept,revoke}` and `POST /internal/v1/organizations/{deprovision,reactivate,suspend}`. go-api is the policy enforcement point and calls them; the go-api proxy never forwards them.

- Each route has a row in `contracts/auth/v1/endpoint-profiles.auth-service.json` that lists the one credential class the route admits, and the binary embeds that document. Every route admits the go-api workload token (`workload_token`) only, so each row lists it alone. With `AUTH_MEMBERSHIP_ROUTES=true`, auth-service refuses to start when any of the ten routes has no such row. It exits 1, and the startup log line (`configure runtime dependencies`) gives `reason` `auth_provisioning_profile_row_missing`, the `route` (for example `POST /internal/v1/memberships/add`) and the `required_classes` its row must list (class names only). That start failure line is an Error line, so every log level shows it. `organizations/state` follows the same rule, but a missing or short row leaves only that route unmounted (it answers 404). That case is logged at Info only (`auth provisioning route not mounted`), so at `AUTH_SERVICE_LOG_LEVEL=warn` or `error` no line names it.
- The caller presents the go-api workload token on the same terms as the session issue route: header `typ` `workload+jwt`, audience `auth-service` and `sub` equal to `AUTH_SESSION_ISSUE_WORKLOAD_SUBJECT` (unset refuses every workload token). The token has no action claim, so one go-api token covers both the session issue and these routes. The `svc_authsess_` credential is retired on these routes: it is refused from the bearer text alone, before any store or key-set read, with the same 401, and every such refusal counts in `auth.provisioning.retired_credential_refusals{operation}` and logs the reason `retired_credential_class` (the answer never names it). The scope `memberships:write` is retired too: no service may hold it and `dho service-credentials create` refuses it. A route takes the workload token only once it is on the route list of that path (every provisioning route is). Any other bearer, a wrong audience or subject and a token the verifier refuses all get the same 401, and a key set that cannot be read is a 503.
- Every audit row a route writes names the human actor (`actor_principal_id`) and the calling credential: `caller_principal_id` and `workload_jti` of the workload token.
- The body is one JSON object of the route's members (at most 4 KiB): a duplicate, unknown or mistyped member, or a non-canonical id, is a 400 `malformed`. Each body names the acting account (`actor_principal_id`, or the joining account's `principal_id` for an accept). An invite's `description` and `request_metadata` go to go-api's `audit_logs` row and are never logged; neither is an invite token or an address.
- auth-service checks go-api's rule again, before anything is read for the request and again inside the write's transaction after its locks: the actor is an active account and a superuser, or an owner or admin member of the organization; a non-superuser may not change a superuser member; a deprovision needs a superuser. Refusals are 403 `principal_deactivated`, `admin_required` or `superuser_required`. An invite create or revoke locks the actor's `auth.principals` and `public.users` rows, and those of the invite's inviter, before that check (the membership writes' lock order), so a demotion or disable of the actor either commits first, and the write is refused, or waits for the write.
- An accept of an invite whose organization the auth schema does not hold yet (an invite go-api made) projects that organization from go-api's row first, as the other writes do before they start. It does this only for a token that names a pending, unexpired invite: an unusable token projects nothing. The token is checked at the first read and the projection commits on its own, so a later refusal (an expiry at the invite lock included) keeps the projected organization, which mirrors go-api's row. An organization go-api does not have either is 400 `invite_invalid`; a slug that another auth organization holds is 409 `organization_conflict`.
- A write's refusals are named `error.v1` reason codes (for example 409 `last_owner`, `organization_suspended`, `already_member`, 404 `membership_not_found`, 400 `invite_invalid` for every unusable token); a store failure is a 503.
- `organizations/deprovision` revokes every pending invite, removes every live membership (both tables each), ends every session of the organization, revokes every live key of its service accounts, suspends the organization's auth copy and frees its slug in one commit with one `auth.organization.deprovisioned` audit row; a repeat is a no-op. The freed slug is `~deleted~<organization id>`, so a new organization may take the deleted one's name and slug; a sign-in projection or backfill from go-api's row never writes the old slug back. A deprovision of an organization that was already suspended with its slug (a plain suspension, or a delete before slugs were freed) frees the slug with one `organization.updated` event and no new suspension. Each revoked key gets `revoked_reason` `org_deprovisioned`, one `auth.service_account.key_revoked` audit row and one `service_account.key_changed` event. Afterwards the membership and invite writes of that organization refuse and its service-account keys answer `revoked`. Every other organization-scoped allow decides on go-api's `public.organizations.is_active`, never on the auth copy the deprovision suspends: until go-api's row is inactive (the delete's purge, or the organization state reconcile below, up to 5 minutes after the deprovision when `AUTH_PROXY_ORG_PROVISIONING=true`), such an allow still reads the organization as active.
- `invites/revoke` ends one pending invite: the body is `organization_id`, `invite_id` and `actor_principal_id`. The actor rule (an active superuser, or an owner or admin member) runs before the invite is read, so a refused actor gets the same 403 for an existing and an unknown invite. The rule runs again under the revoke's locks (the actor's and the inviter's rows, then the organization row). The answers: 200 `{invite_id, status: "revoked"}`, also for a repeat, which writes no second audit row; 404 `invite_not_found`; 409 `invite_not_pending` for an accepted or expired invite (the expiry is checked against the clock read after the invite row lock). A revoke writes no go-api `audit_logs` row.
- `organizations/onboard` creates a user's first organization. The body is `{"principal_id", "organization_name", "description", "request_metadata"}`; it takes no slug, tier or settings. One commit writes the organization and the owner membership in both schemas and go-api's `audit_logs` row. A principal with a membership gets 409 `already_member`, a disabled one 403 `principal_deactivated`, under the principal row lock. A taken slug gets one 8 hex suffix.
- `organizations/create` creates an organization for a superuser. The body is `{"actor_principal_id", "organization_name", "slug", "tier", "managed_by"}` and an optional `organization_description`, `settings` and `owner_principal_id`. The actor rule runs before any read and again under the verb's locks. One commit writes the organization and, when named, its owner, in both schemas.
- `organizations/reactivate` has its row like the other routes. It ends an organization's suspension (a deprovision's included): the body is `{"organization_id", "actor_principal_id"}`, the actor must be an active superuser (read through the users seam, before anything else and again under the organization row lock), and the answer is `{"organization_id", "status": "active", "reactivated"}`. An organization that is not suspended answers 200 with `reactivated` false and writes nothing. A reactivation writes one `auth.organization.reactivated` audit row naming the actor, the `organization.reactivated` event and the revision, in one commit. It does not restore the memberships and invites a deprovision ended, nor the slug a deprovision freed. A suspension in the auth schema ends only by this route: go-api's own `is_active` flows into the schema as a suspension, never as a reactivation.
- `organizations/state` has its row. It answers `{"organization_id", "status", "revision"}` for the organization named by the body `{"organization_id"}`, the status and the revision read in one statement; go-api's `is_active` PATCH sends that revision as `if_revision` to suspend and reactivate, and a stale one answers 409 `state_changed` and writes nothing. It takes the go-api workload token (admitted as the other provisioning routes are), reads no actor and writes no audit row; an unknown organization is 404 `organization_not_found` and a store fault 503 `store_unavailable`.
- `organizations/suspend` mirrors reactivate: the body is `{"organization_id", "actor_principal_id"}`, the actor must be an active superuser (read through the users seam before anything else and again under the organization row lock), and the answer is `{"organization_id", "status": "suspended", "suspended"}`; an organization that is already suspended answers 200 with `suspended` false and writes nothing. It writes one `auth.organization.suspended` audit row naming the actor, the `organization.suspended` event and the revision in one commit. An actor with no `auth.principals` row, or any fault of the store, answers the fail-closed 503 `store_unavailable`. It takes the go-api workload token (admitted as the other provisioning routes are); the audit row names the workload caller and its `workload_jti`.
- `organizations/rename` has its row (no go-api caller yet). The body is `{"organization_id", "actor_principal_id", "name"}` and an optional `if_revision`. The actor must be an active superuser, or an owner or admin member of the organization, checked before anything is read for the request and again under the organization row lock. The name is stripped, then must be 1 to 100 characters (422 `name_invalid`). A suspended organization is 409 `organization_suspended`, and a stale `if_revision` is 409 `state_changed`. The answer is `{"organization_id", "name", "renamed"}`; a rename to the current name answers `renamed` false and writes nothing.
- `service-accounts/create`, `disable`, `enable` and `owner` have their rows and are served with the other provisioning routes (no go-api caller yet). They take the go-api workload token, admitted as the other provisioning routes admit it. The actor is an active superuser or an owner or admin member of the organization, read through the users seam before the verb and again under its locks; create, enable and owner need `AUTH_USERS_OWNED`. An account that does not exist and one of another organization answer a non-superuser alike. The refusals are named `error.v1` reason codes, among them 409 `name_taken`, `owner_invalid`, `owner_not_member`, `already_in_state` and `state_changed`; see the [service accounts runbook](../../operate/runbooks/auth-service-accounts.md).
- `service-accounts/keys/issue`, `rotate`, `revoke` and `list` have their rows and are served with the other provisioning routes (no go-api caller yet). They take the same credential. A key they issue authenticates nowhere yet.
- `grants/create`, `update` and `revoke` have their rows and are served with the other provisioning routes (no go-api caller yet). They take the go-api workload token, admitted as the other provisioning routes admit it. The actor is an active superuser or an owner or admin member of the body's organization, read before the verb and again inside it after its locks; a non-superuser actor may not name a superuser as grantee. A grant gives an active member of the organization the role `viewer`, `member` or `admin` on one repository key (a lowercase path of 2 to 20 segments in at most 255 bytes, `owner/repo` or `owner/group/repo`) or on the explicit organization-wide `*`, with an optional expiry that must lie in the future. A create over a tuple whose only row has expired ends that row (`resource_grant.expired`) and grants; a grant that has not expired is refused as `already_granted`. A grant of another organization and an unknown one answer a non-superuser alike. No answer carries the repository key; the status is `revoked`, then `expired`, else `active`. Verbs need `AUTH_USERS_OWNED`. See [Resource grants](resource-grants.md).
- go-api calls the reactivate route from `PATCH /api/v1/admin/orgs/{org_id}` with `is_active=true`, and the suspend route with `is_active=false`, only when `AUTH_PROXY_ORG_PROVISIONING=true` (chart value `goApi.authProxy.orgProvisioning`, default off, refused unless `authService.extraEnv` sets `AUTH_MEMBERSHIP_ROUTES=true`; needs `AUTH_PROXY_URL` and go-api's workload token, `AUTH_PROVISIONING_CREDENTIAL=workload`). With it on, go-api asks auth-service first, for every found organization (an organization already in that state answers a no-op), and writes `public.organizations` only on a 200; a refusal or an outage answers 503 and writes nothing. With it off the PATCH is unchanged, and auth-service takes a go-api suspension at the next refresh of the organization, so `orgs-reconcile` can list `org_active_diff` until then. With the switch on and the suspend route not mounted (no profile row) every `is_active=false` answers 503.
- With `AUTH_PROXY_ORG_PROVISIONING=true` go-api also compares every organization with `organizations/state` every 5 minutes, one read per organization per replica, and stores auth's state in `organizations.is_active` when the two differ, with one Info line per row (`org_id`, `from`, `to`). A difference is read again with the row locked; a row another transaction holds waits for the next pass. The pass sends at most 5 state reads a second (the re-read included), under the route's default bucket of 20 a second with a burst of 40 per auth pod. A row auth refuses, a 404 included, is left as it is and counted in one WARN per pass (counts only: `refused`, `rate_limited`, `stopped`). A 429 is not a refusal: the pass waits its `Retry-After` (at most 10 s, 1 s when it names none) and reads the same row again; after 5 answers of 429 for one read, or on a read failure, the pass stops, and the next pass starts after the last row it covered. A pass that reaches the last organization starts the next one from the first, and so does a resumed pass that stops before it covers any organization: an organization that stops every pass delays the ones before it to every second pass, and the ones after it are not read until it answers. With the switch off nothing runs. Before the switch is turned on, and again before it is turned back on after a rollback, `dho auth orgs-reconcile` must show `org_active_diff=0`: with the switch off a PATCH suspends in go-api's row only, and the first pass after the flip would clear that suspension to match auth.
- The same switch sends go-api's member, invite and delete writes to these routes: `POST/PATCH/DELETE /api/v1/admin/orgs/{org_id}/members[/{user_id}]` and `.../transfer-ownership` to `memberships/{add,role,remove,transfer}`, `POST /api/v1/admin/orgs/{org_id}/invites` to `invites/create`, `POST /api/v1/auth/accept-invite` and `POST /api/v1/auth/onboard` with `join_org` to `invites/accept`, and `DELETE /api/v1/admin/orgs/{org_id}` (not a dry run) to `organizations/deprovision` after the ClickHouse preflight and before any PagerDuty revoke or purge. `POST /api/v1/admin/orgs` with `owner_user_id` writes the organization row alone, then sends the first owner to `memberships/add` with the calling superuser as the actor; when that add does not land, go-api answers from the owner row if auth-service wrote it, else it deprovisions the organization and deletes its row with one statement that keeps it while any membership exists (an owner go-api does not hold is today's 500 before any write; after the cleanup an actor refusal is its 403 and any other refusal or an outage is 503, where the switch off would add the owner; a failed cleanup is 500 (no retry onto the half-written state) and the ERROR `admin: organization created without its owner`, see the flip runbook). go-api runs its own checks first as before, holds no transaction or row lock during the call and writes none of those rows (nor the `member_invited` or `member_joined` audit rows) itself; it answers from the row auth-service wrote. Each refusal go-api has today's answer for is that answer (for example 409 `last_owner` on a removal is today's 400 "Cannot remove the last owner of an organization"); any other refusal, or an outage, is 503 and nothing is written. A deprovision 404 (auth-service holds no such organization) lets the delete go on. The chart refuses the switch below `authService.phase` 4: the routes refuse until auth-service owns users. With the switch on, two rules are stricter than go-api alone: an add or invite with a role outside `owner`, `admin`, `member`, `viewer` is 400 "Invalid role: <role>", and a role change away from the last owner is 400 "Cannot remove the last owner of an organization". `AUTH_USERS_OWNED` with the stage `owned` and the switch off leaves go-api's member writes in the public tables only; set the switch with the flip (runbook). The operator CLI (`dho admin`) sends `users update` with `--org` or `--remove-from-org` and a real `orgs delete` (a dry run still runs) to the same routes whatever the switch says, with `--actor` as the actor, `AUTH_PROXY_URL` and go-api's workload token (the workload inputs `AUTH_WORKLOAD_SUBJECT_FILE` or `AUTH_WORKLOAD_BOOTSTRAP_FILE`, and `AUTH_WORKLOAD_ISSUER`, of the pod it runs in) as the route and credential, and refuses without them. With the switch on, `orgs create` with `--owner-email` still refuses with a message naming the switch, before any database write: done there, it would change go-api's rows only.
- Credential steps: set `AUTH_SESSION_ISSUE_WORKLOAD_SUBJECT` to go-api's workload principal. The `memberships:write` scope is retired: nothing mints it (the `service-credentials` verbs are gone), and a `svc_authsess_` credential gets a 401 on these routes.
- Provisioning credential (go-api): with `AUTH_PROXY_ORG_PROVISIONING=true`, go-api's member, invite, delete, reactivate, suspend and rename calls present go-api's workload token (audience `auth-service`) to auth-service, and read no `AUTH_SESSION_ISSUE_TOKEN` for these calls. The `svc_authsess_` credential is retired on these routes, so there is no other choice: `AUTH_PROVISIONING_CREDENTIAL` may stay unset, empty or `workload`; `session_compat` and any other value is a start-up error.

  | Environment | Rule |
  | --- | --- |
  | `AUTH_PROVISIONING_CREDENTIAL` | unset, empty or `workload`; `session_compat` is a start-up error (retired). |
  | `AUTH_WORKLOAD_SUBJECT_FILE` | Required with the switch on: path of the projected ServiceAccount token file (Kubernetes). Set exactly one of this and `AUTH_WORKLOAD_BOOTSTRAP_FILE`. |
  | `AUTH_WORKLOAD_BOOTSTRAP_FILE` | Required with the switch on: path of the workload bootstrap credential file (Compose). |
  | `AUTH_WORKLOAD_ISSUER` | Required with the switch on: auth-service's token issuer URL (`AUTH_TOKEN_ISSUER_URL`, https); every workload token must carry it. |

  The exchange goes to the origin of `AUTH_PROXY_URL` (`POST /internal/v1/token/exchange`, which auth-service mounts only while `AUTH_WORKLOAD_EXCHANGE` or `AUTH_WORKLOAD_BOOTSTRAP` is `true`; see [workload-token exchange](#workload-token-exchange)); the subject file is read again for every exchange, and one exchange serves all the clients that selected `workload` (the provisioning clients and the session issue client). With the switch on, a missing or invalid input is a start-up error naming it. A failed exchange fails that call (503) with no request to the provisioning routes; there is no fallback to `svc_authsess_`.

### User-admin routes

With `AUTH_USERS_OWNED=true`, auth-service serves the writes of go-api's `/api/v1/admin/users` routes: `POST /internal/v1/users/{create,update,password,delete}`. They are not behind `AUTH_MEMBERSHIP_ROUTES`.

- Each route has a row in `contracts/auth/v1/endpoint-profiles.auth-service.json` that admits the go-api workload token (`workload_token`) only, and the binary embeds that document. The four routes mount together or not at all: a document that lacks one row, or a row that lists another class, leaves all four unmounted (404). This is no start refusal.
- At start, auth-service logs one INFO line `users routes` with `mounted` (`4/4` or `0/4`). With `0/4` it adds `reason`: `users_not_owned`, or `auth_provisioning_profile_row_missing` with the `route` that has no row.
- The caller presents the go-api workload token as on the provisioning routes: audience `auth-service` and `sub` equal to `AUTH_SESSION_ISSUE_WORKLOAD_SUBJECT`. Any other bearer is the one `401 invalid_credentials`: a workload token of another subject or audience, a user token, the retired `svc_authsess_` credential, or no token.
- The tenant class is `org_scoped`, as the go-api rows of `/api/v1/admin/users`: the actor is an active platform admin, or an owner or admin of the organization the body names. The rule runs again after the platform role write lock.
- go-api does not call these routes yet.

### Delegated impersonation (go-api)

- `AUTH_PROXY_IMPERSONATION` (go-api; chart value `goApi.authProxy.impersonation`, default off; `true` or `false`, or any other value `strconv.ParseBool` reads (`1`, `t`, `T`, `TRUE`, `True`; `0`, `f`, `F`, `FALSE`, `False`), as for every `AUTH_PROXY_*` flag; any other value leaves the switch off and go-api starts, with one WARN line that names the variable and the value's length, never the value). On, go-api's `POST /api/v1/admin/impersonate` asks auth-service to start a [delegated session](delegated-sessions.md) of the caller's own session, and `POST /api/v1/admin/impersonate/stop` ends it there. auth-service writes go-api's impersonation row and its audit rows; go-api writes neither. Off (or unset), go-api starts and ends its own impersonation row as before.
- It needs `AUTH_PROXY_SESSIONS=true` and `AUTH_PROXY_URL`. go-api does not refuse to start without sessions: it logs one ERROR line, sets `devhealth_api_auth_proxy_impersonation_config_invalid` to 1, and every start and stop answers 503. The chart refuses `goApi.authProxy.impersonation=true` below `authService.phase` 2, so a chart render cannot produce that state.
- query-api reads the same `AUTH_PROXY_IMPERSONATION` (`true` or `false`; any other value starts the process with one WARN naming the variable and refuses, as with the switch on). The chart renders it for query-api from `goApi.authProxy.impersonation`, and `queryApi.extraEnv` may not set it. On, query-api refuses the administrator's own bearer beside a live impersonation row on `/graphql`, `/query` and `/query/proof-write` with `403`; see [query-api](authn-authz.md#query-api).
- Do not turn it on before the web change that swaps the browser session to the delegated token at start and restores it at stop is live.
- `AUTH_PROXY_SERVICE_ACCOUNT_KEYS` (go-api; default off; `true` or `false`, any other value is a start-up error; set through go-api's extra env, there is no chart key yet). On, the platform-admin routes `GET /api/v1/admin/service-accounts/{service_account_id}/keys`, `POST /api/v1/admin/service-accounts/{service_account_id}/keys` (issue), `POST /api/v1/admin/service-accounts/{service_account_id}/keys/rotate` and `POST /api/v1/admin/service-accounts/keys/{credential_id}/revoke` call auth-service's `/internal/v1/service-accounts/keys/{list,issue,rotate,revoke}` with go-api's workload token (audience `auth-service`, the provisioning credential: `AUTH_PROVISIONING_CREDENTIAL` unset, empty or `workload`) and the caller as the actor. go-api passes auth-service's answer through: an issue or rotate receipt carries the key's secret once, with `Cache-Control: no-store`, and go-api logs no part of it. auth-service runs its actor rule and writes the key, the audit row and the `service_account.key_changed` event; go-api writes nothing. The routes take `auth.service_accounts` ids only: a legacy `users` row with `auth_provider` `service` answers 404. Only a holder of `admin.users` (a superuser) passes the gate; an organization admin answers 403. Off (or unset), the routes stay mounted and answer 503 `config_missing`. It needs `AUTH_PROXY_URL`, and auth-service must mount the key routes (`AUTH_MEMBERSHIP_ROUTES=true`).
- The same switch carries the platform-admin service account lifecycle routes: `POST /api/v1/admin/service-accounts` (create; body `organization_id`, `owner_principal_id`, `name`), `POST /api/v1/admin/service-accounts/{service_account_id}/disable`, `.../enable` and `.../owner` (body `owner_principal_id`). On, they call auth-service's `/internal/v1/service-accounts/{create,disable,enable,owner}` with the same workload token and the caller as the actor, and pass auth-service's answer through; auth-service runs its actor rule and writes the account, the audit row and the event. Only a holder of `admin.users` passes the gate; an organization admin answers 403. Off (or unset), these four routes are not mounted: their paths answer `404` `{"detail":"Not Found"}` as before. A legacy `users` row with `auth_provider` `service` answers 404.
- With the switch on, a start answers `200` with `status`, `target_user` (`id`, `email`, `org_id`, `role`), `expires_at`, `access_token`, `token_type` (`bearer`), `expires_in` and, under the eddsa class only, `session_access_token`. The session lasts at most 15 minutes and has no refresh. A caller whose token carries no auth-service session (`sid`) is refused `409` "Impersonation needs an authentication-service session; sign in again", at start and at stop. Any failure to start or end the session at auth-service is `503` and changes nothing in go-api; there is no fallback to a go-api session.
- Stop needs the administrator's own session: the delegated bearer is refused on every `/api/v1/admin` route, and `POST /api/v1/admin/impersonate/stop` is decided by the PDP with the administrator's own bearer. go-api refuses an impersonation caller fail-closed on PDP-enforced rows (outcome `impersonation_refused`); the stop route is exempt from that refusal.

### Shadow PDP (go-api)

go-api can ask the policy decision point (`POST /v1/authorize` on auth-service) beside its own guard and compare the two answers. It is telemetry only: the legacy answer always wins, no response changes, and the shadow reads no database. It is off by default. A bad or missing input turns it off, logs an ERROR naming the variable (never its value), sets `dev_health_api_shadow_config_invalid` to 1 (see [readiness and SLO](readiness-and-slo.md#metrics)) and never fails the start.

| Environment | Rule |
| --- | --- |
| `AUTH_SHADOW_PDP` | `true` or `false`; unset or empty is `false`. Any other value turns the shadow off and counts as a bad value. |
| `AUTH_SHADOW_PDP_HIGH_RISK` | `true` or `false`; unset is `false`. High-risk rows write one PDP audit row per decision, so keep it off. |
| `AUTH_SHADOW_PDP_SAMPLE` | Whole number, 1 to 100: the share of covered requests that ask. Unset is 100. |
| `AUTH_SHADOW_PDP_MAX_IN_FLIGHT` | Whole number, 1 or more: the bound on calls in flight; a call over it is dropped and counted. Unset is 32. |

With `AUTH_SHADOW_PDP=true` the call goes to the origin of `AUTH_PROXY_URL` (required; when it is malformed and no `AUTH_PROXY_*` flag is on, only the shadow turns off, with an ERROR naming `AUTH_PROXY_URL`, and the start goes on; with the shadow off, or with a flag on, a malformed `AUTH_PROXY_URL` still stops the start) and presents go-api's workload token (audience `auth-service`), with each call limited to 2 seconds. The workload client is the one the provisioning and session issue credentials share when one of them chose `workload`; otherwise go-api builds one from `AUTH_WORKLOAD_SUBJECT_FILE` or `AUTH_WORKLOAD_BOOTSTRAP_FILE` (exactly one) and `AUTH_WORKLOAD_ISSUER`, as for the provisioning credential above. None of those inputs is read while the shadow is off. An unreachable PDP does not matter at start: the client is lazy, and a failed call counts as `error`.

The shadow covers only requests that carry an EdDSA user access token; a legacy HS256 token, an impersonation and a request with no organization are `skipped`, so a zero mismatch count is no proof of parity for those callers. auth-service must list go-api's workload principal in `AUTH_AUTHORIZE_CALLER_SUBJECTS` before the shadow is turned on, and its per-pod rate limit applies to the PDP route.

### PDP gate (query-api)

query-api can ask the policy decision point (`POST /v1/authorize` on auth-service) on its REST routes (`/api/v1/*`). It asks for a caller that presents an EdDSA user access token, after query-api's own token and organization checks have accepted it, with the row's catalog action and the caller's organization. GraphQL operations (`/graphql`, `/query`, the MCP listener) are decided per root field; see [GraphQL root fields](#graphql-root-fields-query-api).

Two settings work together. `QUERY_API_PDP_MODE` builds the client. `QUERY_API_AUTHZ_ENFORCE` (the 5.17 cells) decides which routes the decision replaces: a route is enforced only while the cell of its action's namespace is on, whatever the mode. With the cell off, `shadow` asks in the background and never changes a response; `enforce` never acts as `shadow`: on a route whose cell is off it answers 503 `{"detail":"Authorization unavailable"}` (log reason `authz_enforce_cell_off`) and asks nothing.

| Environment | Rule |
| --- | --- |
| `QUERY_API_PDP_MODE` | `off`, `shadow` or `enforce`; unset or empty is `off`. `off` builds no client, reads no other PDP input and asks nothing. `shadow` and `enforce` build the client. On a route whose cell is off, `shadow` hands the legacy answer of each mapped REST route, and of each GraphQL root field of an operation on `/graphql` or the MCP listener (one observe per distinct action, organization and verdict, at most 7 per operation; the rest count `skipped` with reason `cap`), to the shared 5.12 shadow, which asks the PDP in the background, counts and compares, and never changes a response; it counts on `dev_health_api_shadow_results_total` and `dev_health_api_shadow_mismatch_total`, and reads `AUTH_SHADOW_PDP_SAMPLE`, `AUTH_SHADOW_PDP_MAX_IN_FLIGHT` and `AUTH_SHADOW_PDP_HIGH_RISK` as go-api does (a bad value never fails the start: one ERROR names the variable and `dev_health_api_shadow_config_invalid` is 1). `enforce` refuses with 503 on a route whose cell is off. |
| `QUERY_API_AUTHZ_ENFORCE` | Comma list of catalog action namespaces (`analytics`, `metrics`, `git`, `work_items`, ...); unset is none. Read once at start by `internal/authzenforce`; an item that is not a namespace, a repeat, an empty item and `*` are ignored and stay off (one ERROR line, the `dev_health_authz_enforcement_ignored_items` gauge), never a start failure. On a route of a listed namespace the decision replaces the legacy answer: a PDP deny is 403 `{"detail":"Not authorized"}`; no verdict (the PDP is down, a timeout, a 429, a bad answer) is 503 `{"detail":"Authorization unavailable"}`; a listed namespace with no client (`QUERY_API_PDP_MODE` off or misconfigured) is 503 with log reason `authz_enforce_no_decision_point`. The route's handler is not reached. |
| `QUERY_API_HEADERS_AUTHZ_ENFORCE` | The same list form, for the GraphQL operations of the `X-DH-Internal-*` header carrier (the MCP listener, `/query` on the internal listener). That carrier has no principal the PDP can judge, so a root of a listed namespace refuses its operation with `authz_enforce_no_principal`; unset, it stays on today's path. `QUERY_API_AUTHZ_ENFORCE` never judges it. |
| `AUTH_PROXY_URL` | auth-service's base URL (go-api's setting): an http(s) origin with no path, query or credentials. Read only while the mode is `shadow` or `enforce`. |
| `AUTH_WORKLOAD_SUBJECT_FILE`, `AUTH_WORKLOAD_BOOTSTRAP_FILE`, `AUTH_WORKLOAD_ISSUER` | query-api's workload credential, with go-api's rules (exactly one file, readable; an https issuer). Read only while the mode is `shadow` or `enforce`. |

An allow on an enforced route is served only when query-api carries out every obligation it carries. The decision's `organization_id` and its `tenant_scope` must both be the caller's organization, compared as UUIDs (the RFC 9562 36-character text form, any case, by canonical form); a value that does not parse is refused. `repository_scope` `organization`, or a `repository_allowlist` that holds `*`, serves every repository of the tenant. Any other `repository_allowlist` (an empty one included) is carried out only on a route whose class the route-class registry narrows (`internal/queryapi/pdp/routeclass.go`, the one gate point); no class is narrowed yet, so today such an allow is 503. Every REST row has a class, the label its handler passes to the authenticator. A class is N when every response read is keyed by repository, and M when some read has no repository column (the whole route stays M). An allowlist on an M route is 503 `allowlist_route_unsupported`; on an N route that is not narrowed yet it is 503 `pdp_unknown_obligation`. The route class is in the log line (`route_class`), never in a metric label. An allow with neither repository member, any `redaction` class, a `minimum_assurance` above `aal1` (every session query-api accepts is `aal1`) or `step_up` is 503. No field is redacted. The log line names the closed reason only (`tenant_scope_mismatch`, `pdp_unknown_obligation` for an obligation query-api cannot apply yet, `allowlist_route_unsupported`, `repository_scope_absent`, `authz_enforce_cell_off`, `authz_enforce_no_decision_point`), never a value.

A bad mode value, or `shadow`/`enforce` with a missing or bad input, never fails the start. query-api logs one ERROR naming the variable (never its value or a path), sets `dev_health_query_api_pdp_config_invalid` to 1, and answers 503 `{"detail":"Authorization unavailable"}` to every request that would ask the PDP. Each call presents query-api's workload token (audience `auth-service`, client service `dev-health-query-api`) and is limited to 2 seconds; the workload registry row `query-api` holds that audience.

query-api has no exempt credential class. The HS256 edge token (`ops_access_token_hs256`) and the effective-principal envelope (`effective_principal_envelope`) are retired: on every route each gets the answer of an unaccepted bearer, so `dev_health_query_api_pdp_exempt_total` (labels `class`, `action`) stays at zero. PDP asks count in `dev_health_query_api_pdp_results_total` in enforce mode (labels `mode`: `enforce`, `invalid`; `result`: `allow`, `deny`, `unavailable`, `not_configured`, `not_carried_out`, `no_decision_point`, `no_org`; `action`). `no_org` is an enforced row or GraphQL operation asked with no organization (only a superuser passes with none): it keeps today's answer with no PDP call. `dev_health_query_api_pdp_enabled` is 1 while a shadow or enforce gate is built. In shadow mode a caller that is not a user access token is counted `skipped` on the shadow counter and never asks the PDP. `dev_health_query_api_pdp_config_invalid` is also 1 while a namespace is listed with no client. `dev_health_authz_enforcement_enabled` (labels `namespace`, `service` `query-api`) shows the cells.

#### GraphQL root fields (query-api)

Every GraphQL server (`/graphql` and `/query`, the MCP listener) decides an operation's root fields after the org guard has admitted the operation, before any resolver runs. Each root names its catalog action (`internal/queryapi/graph` field action table); a root is decided while the cell of its action's namespace is on in the caller's cell list. The class is the bearer the ingress authenticated: a user access token follows `QUERY_API_AUTHZ_ENFORCE`; the HS256 edge token and the envelope never reach an operation, because every ingress refuses them; no bearer is the header carrier, which follows `QUERY_API_HEADERS_AUTHZ_ENFORCE` and, having no principal, is refused (`authz_enforce_no_principal`) when its cell is on. Every ingress sets a scope on the request; an operation without one is refused (`authz_enforce_no_scope`) while a cell of one of its roots is on in either list. With every cell of an operation's roots off the operation runs as today; in `enforce` mode a user caller's root whose cell is off is refused (`authz_enforce_cell_off`), as on the REST routes. A superuser with no organization keeps today's answer and is not asked about (`no_org`), as on the REST routes. The internal listener's own routes (`/query/proof-write`, `/query/run-operation`) and the MCP listener carry the process's gate like the public routes, and `/query` hands the operation the bearer it authenticated, so these rules hold on every GraphQL ingress.

The decided roots are asked about together, for the organization the operation is served for (the caller's, or the one a verified superuser names; the PDP judges that organization, with no local superuser bypass): one ask per distinct action. The obligation rules are the REST ones above, per root key (query-api keeps a registry of the roots that carry an allowlist; it is empty, so an allowlist other than `*` is refused). The allows merge into one scope for every decided root (two allowlists: their intersection; an allowlist with an organization-wide allow: the allowlist). Any refusal answers the whole operation with no data: a PDP deny is `{"errors":[{"message":"Not authorized","extensions":{"code":"FORBIDDEN"}}],"data":null}` with HTTP 200, the org guard's form; no verdict or an obligation not carried out is `{"errors":[{"message":"Authorization unavailable","extensions":{"code":"SERVICE_UNAVAILABLE","reason":"<closed reason>"}}],"data":null}`, HTTP 503 on `/graphql` and `/query`. The MCP listener answers the same body with HTTP 503, or 403 for a deny. A decided root is not shadowed.

Before the mode is turned on: query-api needs a workload binding (`auth-migrate workloads bind -workload query-api ...`), auth-service must list query-api's workload principal in `AUTH_AUTHORIZE_CALLER_SUBJECTS`, and its per-pod limit on the PDP route applies. A delegated (impersonation) token and a caller with no organization are decided by the PDP like any other user token.

### Workload token exchange

The route `POST /internal/v1/token/exchange` is internal: go-api never forwards it. It is mounted while
`AUTH_WORKLOAD_EXCHANGE` or `AUTH_WORKLOAD_BOOTSTRAP` is `true`, and each switch turns on one subject. Both need
`AUTH_TOKEN_ISSUER_URL` (the `iss` of the workload tokens it signs). Any other value than `true` or `false` fails
startup. The values are not secrets: a path names a file, and the files hold the secrets.

| Environment | Default | Rule |
| --- | --- | --- |
| `AUTH_WORKLOAD_EXCHANGE` | `false` | `true` turns on the Kubernetes subject: a projected ServiceAccount token, reviewed by the cluster API server (TokenReview). Needs the five settings below. |
| `AUTH_WORKLOAD_TRUST_DOMAIN` | unset | Required with the Kubernetes subject. Non-empty, at most 253 bytes, no surrounding whitespace. Names this cluster in the workload bindings. |
| `AUTH_WORKLOAD_EXCHANGE_CLUSTER_ISSUER` | unset | Required with the Kubernetes subject. At most 512 bytes, no surrounding whitespace. The `iss` of the cluster's ServiceAccount tokens; a binding's `-issuer` must equal it. |
| `AUTH_WORKLOAD_EXCHANGE_KUBE_API_URL` | unset | Required with the Kubernetes subject. An https origin: `https://host[:port]`, no path, query, fragment or credentials. |
| `AUTH_WORKLOAD_EXCHANGE_KUBE_CA_FILE` | unset | Required with the Kubernetes subject. Absolute, clean path of the PEM bundle that the API server certificate must chain to. No other root is trusted. |
| `AUTH_WORKLOAD_EXCHANGE_REVIEWER_TOKEN_FILE` | unset | Required with the Kubernetes subject. Absolute, clean path of auth-service's own token, which may create `tokenreviews`. Read again on every review (at most 16 KiB). |
| `AUTH_WORKLOAD_BOOTSTRAP` | `false` | `true` turns on the Compose bootstrap credential subject. It reads no other setting. |

Compose profile the bootstrap subject is set up by the
[bootstrap credential runbook](../../operate/runbooks/auth-workload-bootstrap-credential.md). The registry the
exchange reads is in the [workload registry](workload-registry.md). The reasons that a refused exchange logs are in

### Authorize routes

`POST /v1/authorize` and `POST /v1/authorize:batch` are the policy decision point (authorization_request.v1 in, authorization_decision.v1 or authorization_batch_response.v1 out). `POST /v1/authorize:repositories` (one request in, one decision out) mounts the same way. Each route mounts only when `contracts/auth/v1/endpoint-profiles.auth-service.json` holds its row admitting `workload_token`. Without the row the route answers 404, and the startup log has an Info line `auth authorize route not mounted` with the `route`.

- With `AUTH_AUTHORIZE_CALLER_SUBJECTS` set (comma-separated workload principal ids, `prn_` and 22 base64url characters each, no repeats; it needs `AUTH_TOKEN_ISSUER_URL`; default unset, which refuses every caller), a caller presents its own workload token: header `typ` `workload+jwt`, audience `auth-service`, `sub` in the list. A wrong audience or an unlisted subject is refused before the key set or any table is read. Every refused caller gets 401 `invalid_credentials`.
- `principal_reference` is the end user's EdDSA access token (`typ` `at+jwt`, audience `dev-health-api`, scope `api:access`). An HS256 token, a workload token, an `auth-service` audience token, an expired token or a token whose session is revoked, expired or another principal's is refused for the whole call with 401 `principal_reference_invalid`. That code is distinct from the caller's `invalid_credentials`.
- A second `principal_reference` kind, the web approver reference, is on only when `AUTH_AUTHORIZE_WEB_APPROVER_ISSUER`, `AUTH_AUTHORIZE_WEB_APPROVER_JWKS_FILE` and `AUTH_AUTHORIZE_WEB_APPROVER_CALLER` are all set and the caller is also in `AUTH_AUTHORIZE_CALLER_SUBJECTS`; any other state leaves it off with one ERROR line that names the missing settings, and auth-service still starts. web signs the reference with its ACR web assertion key for one device or consent approval, and acr-api checks it against that approval's web assertion and forwards it. Only the caller in `AUTH_AUTHORIZE_WEB_APPROVER_CALLER` (acr-api) may present it, and that caller may present no other kind. The reference has `typ` `web-approver+jwt`, audience `auth-service` (the same audience as the caller's workload token; the `typ` and the key set keep them apart), `iss` equal to `AUTH_AUTHORIZE_WEB_APPROVER_ISSUER`, a life of at most 30 seconds with 5 seconds of clock skew, `sub` the user's principal id as a canonical uuid, `sid` a session.v1 session id, `impersonating` false and `action` `acr.credential.issue`. The keys come from the JWKS file (the same public keys acr-api verifies web assertions with), read on every reference; a key past its `retire_after`, or with a `retire_after` more than 24 hours ahead, is refused, and an unreadable file is 503. The reference answers only `acr.credential.issue` on a resource of type `organization` whose key and organization are the reference's `org_id`, on `POST /v1/authorize` only; any other question, the batch route and the repository route refuse it for the whole call. Its session is read live on every call and the decision cache is never used. The reference is not specific to one approval here: for its 30 seconds it proves that the user's session is live and may issue in the organization. acr-api binds it to one approval. The architecture page with the sequence and component diagrams and every signed token is the device approval page of the web repository (auth-acr-device-approval); the sequence source is `internal/auth/authapi/web_approver_reference.mmd`, beside its Go owner `internal/auth/authapi/authorize_web_approver.go`.
- In the Helm chart (deploy/helm/dev-health) the three settings come from one key, `authService.webApprover`: `issuer`, `caller` (the acr-api workload principal; it must also be in `AUTH_AUTHORIZE_CALLER_SUBJECTS`) and `jwks.secretName` (with `jwks.secretKey`, default `web-jwks.json`), set together or not at all. A partial key fails the render with one message that names every missing key. Set, the chart mounts the Secret as a whole directory at `/run/auth/web-approver` (no `subPath`, so a rotation of the Secret, which it shares with acr, reaches the pod without a restart) and renders `AUTH_AUTHORIZE_WEB_APPROVER_JWKS_FILE=/run/auth/web-approver/jwks.json` with the issuer and the caller. `authService.extraEnv` refuses the three names. Empty renders nothing.
- The body is at most 16 KiB (single) or 256 KiB (batch, 1 to 100 requests). A larger body is 413. A member the contract does not define, a repeated member, a member in another case or a mistyped value is 400 `malformed`.
- Every state read of a call (the session, the principal, go-api's users and memberships rows, the organization and the repository grants) runs in one `READ ONLY REPEATABLE READ` transaction. A read failure, or a decision the core could not make for want of state, is 503 `store_unavailable` for the whole call, never a decision. A key set that cannot be read is 503 `dependency_unavailable`.
- Items of a batch are decided apart: a deny of one item never changes another.
- `expires_at` is the decision time for every deny and for every allow except a repository allow, which keeps the core's 30 s bound.
- Each decision is logged at Info with `decision_id`, `allowed` and `reason_code` only.
- A decision on an action the policy catalog classes high risk (`risk_class` `high`), allow or deny, writes one `auth.authorize.high_risk_decided` audit row before the answer is served. One call writes all its rows in one transaction. The row has the user principal as actor, the caller's workload principal and token id as `caller_principal_id` and `workload_jti`, and the closed attributes `decision_id`, `decision_reason_code`, `action_key`, `resource_type` and `policy_revision`, plus `resource_id` for a repository key. A platform-admin allow has `decision_reason_code` `allowed_by_platform_admin` and no `decision_internal_reason`. It holds no token, session id, request text or organization text the decision did not find. If the rows cannot be written the whole call is 503 `store_unavailable`, for an allow and for a deny. A low-risk decision and a decision on an action outside the catalog write no row.
- A decision for a delegated (impersonation) session, allow or deny, at any risk class, writes one `auth.authorize.delegated_decided` audit row in the same transaction. The row has the real actor as actor (no actor when the session row names none), the target user as subject, the closed attributes of the high-risk row, and the delegated session as `target_kind` `session` and `target_id` (its id, not the token). A delegated high-risk decision writes both rows. A low-risk decision of a session that is not delegated still writes no row.

### Internal listener

With `AUTH_SERVICE_INTERNAL_HTTP_ADDR` set, auth-service opens a third listener for the policy enforcement points (PEPs). Unset, there is no such listener.

- It serves `POST /internal/v1/token/exchange`, `POST /v1/authorize`, `POST /v1/authorize:batch`, `POST /v1/authorize:repositories` and `POST /internal/v1/acr/credential-events` alone, each only while it is mounted (see [workload token exchange](#workload-token-exchange) and [authorize routes](#authorize-routes)). Every other path is 404 there, the operator paths too.
- `POST /internal/v1/acr/credential-events` is internal-only: the API listener answers 404 for it. It mounts only with `AUTH_ACR_EVENTS_WORKLOAD_SUBJECT` and its endpoint-profile row. With the subject unset, auth-service starts and the route is not mounted on either listener. With the subject set and the internal listener off, auth-service starts, the route is served on no listener, and one WARN line says so (`auth internal-only route served on no listener`).
- It trusts no proxy. `AUTH_SERVICE_TRUSTED_PROXIES` is the API listener's alone: here the client address is always the TCP peer, `X-Forwarded-For` is not read, and a caller's `X-Request-ID` is logged as `untrusted`.
- A caller is identified by its own token: the exchange by its ServiceAccount token, the authorize routes by its workload token and `AUTH_AUTHORIZE_CALLER_SUBJECTS`. The refusals are the same as on the API listener.
- The request timeout, the body bound and the rate limits are the API listener's settings. Each route has its own bucket on each listener of each replica.
- Its access lines and request metrics carry `listener` `internal`.
- The API listener does not change: it serves the same routes as without the internal listener.

The chart renders it from `authService.internal` (off by default): the arg, a Service `<fullname>-auth-service-internal` and a NetworkPolicy of the same name that admits only the pods of `authService.internal.peers` (`web`, `query-api`, `go-api`) on `authService.internal.port` (default `8097`).

`authService.networkPolicy.workloadClients` (default `[]`) adds workloads outside the release, for example acr-api, to that internal policy alone, as more `from` entries. Each entry is a non-empty `podSelector` and an optional non-empty `namespaceSelector`; any other key (a port, an `ipBlock`) fails the render, so an entry never opens the API port. It needs `authService.internal.enabled`; with it, `authService.internal.peers` may be empty, but not both lists. The network entry only opens the port: the exchange still refuses a ServiceAccount that is not registered.

The run is bounded to five minutes. Each migration's lock wait is bounded to 5 s
(`lock_timeout`, set on that migration's transaction only), with 3 attempts and
a 5 s pause between them; when every attempt times out, the run fails and logs a
warning per attempt. See
[database, roles and migrations](../../contribute/architecture/auth-control-plane-database.md).

## Secret handling

- **Direct value versus `_FILE`.** For a DSN, set `KEY` **or** `KEY_FILE`; both
  is a configuration error, never a silent choice. A `_FILE` value must name a
  readable file with a non-empty value; one trailing newline is removed and no
  other whitespace is touched. A read failure names the key and a fixed error
  class, never the path or the content.
- **The signing key is a file only.** `AUTH_SIGNING_KEY_FILE` is the path itself
  (there is no `AUTH_SIGNING_KEY_FILE_FILE`). A direct-value **`AUTH_SIGNING_KEY`
  is rejected at load** (ACP-ADR-02 section 4), not ignored.
- **The key set.** `AUTH_SIGNING_KEYSET_FILE` names a JSON manifest,
  `{"keys": [{"kid": "auth-2026-10", "state": "active", "file": "auth-2026-10.pem"}]}`.
  `state` is one of `pending`, `active`, `retiring`, `retired`, `compromised`;
  exactly one key is `active` and signs; `pending`, `active` and `retiring` keys
  are published. `file` is a bare name in the manifest's own directory. The
  manifest is closed (an unknown member is refused) and follows the key file
  contract below (at most 16 KiB). It is re-read on every use, so replacing it
  by an atomic rename rotates the set with no restart; give a new key a new
  file. A kid the process has seen `compromised` never signs again in that
  process. The single key form is a one-key set whose key is `active`.
  The Helm chart renders the single key form by default. With
  `authService.keySet.enabled` it renders this manifest (kid, state and file
  only) into a ConfigMap, stages each named key from its own Secret at mode 0400,
  and passes `--signing-keyset-file`; `authService.keySet` replaces
  `authService.signingKey`, and `AUTH_SIGNING_KEYSET_FILE` stays refused in
  `authService.extraEnv`. The pod holds a static copy, so a change to the set is
  a new rollout, not a live rename.
- **The key file contract**, checked live on every readiness request: a regular
  file opened with `O_NOFOLLOW` (a symlink is refused), at most 8 KiB, mode with
  **no group or world bit** (`0600` or tighter), exactly one `PRIVATE KEY` PEM
  block that parses as an Ed25519 PKCS#8 key. Readiness also signs a probe with
  the active key and verifies it under the published public key. On Kubernetes this needs the key
  staging described in [deployment](../../contribute/architecture/auth-control-plane-deployment.md).
- **Redaction.** DSNs and their passwords are registered with the redactor;
  configuration errors that could quote a value pass through it before they are
  written. The startup log carries `database_configured` and
  `signing_key_configured` as booleans, never a path or a value.
- **DSN form.** Either a URI (`postgres://user:pass@host/db`, with reserved
  characters in the password percent-encoded) or the libpq keyword form
  (`host=... user=... password='...' dbname=...`), which the Compose profile uses.
