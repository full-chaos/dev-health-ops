## Summary
The five fixes of `dho backfill normalize-investment` that D5949 asks for BEFORE any apply. STACKED on #4013 (head 158a3f2493865964f96a4673b81b0c947b7c66da merged in; #4013's files and this PR's do not overlap).
1. REPOSITORY THROUGH THE ENTITY TREE. The item query no longer joins the classification's own `repo_id` to `work_items.repo_id`. A pull request / merge request item (`work_items.type` pr / merge_request) keeps its own repository. Every other item reaches repositories only through `work_graph_issue_pr` (all three tiers count; the strongest, native > explicit_text > heuristic, is named in the row's evidence and counted in the report). Several repositories: the item's effort is split by the churn (additions + deletions) of the linked pull requests per repository, the rule the canonical units use (`units.AllocateRepoEffort`, `pr_churn`: weight = repository churn / total churn); the last repository takes the remainder so the repositories sum to the item's effort exactly. One `work_unit_investments` row per item (`repo_id` only when it spans exactly one repository, the canonical rule) plus one `work_unit_repo_effort` row per repository. An issue whose links carry no churn has no weight to split by: counted "no repository reachable" (the canonical rule gives that case no repository either), never guessed.
2. ALREADY COVERED. An item named in the evidence (`issues`, `prs`) of a canonical unit (any status except `normalized_legacy`) is skipped and counted. The rule is the readers' own from the CHAOS-9206 purpose read (`_records/9206/purpose-read.md`: 14,432 of 16,249 prod items): a pull request reference `<repo uuid>#pr<N>` is turned into the item id form (`ghpr:` and `gh:` for GitHub, `gitlab:...!N`). It REPLACES the repository-day skip: that rule dropped an item because ANY categorized unit shared its repository and day, which is not "the same work described twice" and is a wrong guess when the item is not named.
3. VISIBLE TO READERS OF AN ORG WITH A MEMBERSHIP RUN. `investmentMembershipScopeFilter` (the one shared source, `LatestWorkUnitInvestmentsSource`) admits `categorization_status = 'normalized_legacy'` (qualified column: the SELECT aliases an aggregate of the same name, ClickHouse code 184); `latestInvestmentClockSource` and its write-side twin (`membership_marker_lag.go`) ignore those rows, so writing them does not move the scope state.
4. SECOND APPLY WRITES NOTHING. The plan reads the stored normalized rows (id, input hash, mapping version); an identical row is counted "already stored, not rewritten" and not written. The input hash now covers the repositories, weights, tier and effort. Rows and run ids of the first apply stay; `--rollback --run <first run id>` restores the before-state (also for `work_unit_repo_effort`, which rollback now deletes by unit id prefix and run id).
5. DRY-RUN TABLE: items read; skipped not completed on the classified day; skipped already covered; skipped no repository reachable (by reason); unmatched; unmapped; already stored; rows (normalized) by theme / sub-theme / rule / tier; repository effort rows. Every item is counted in exactly ONE bucket (`Report.Accounted() == Items`, asserted).
